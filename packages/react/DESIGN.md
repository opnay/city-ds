# @opnay/city-ds-react 디자인 가이드

이 문서는 `@opnay/city-ds-react`로 운영 도구, 대시보드, 폼을 설계할 때 적용하는 기준입니다. 사람과 코드 에이전트 모두 컴포넌트를 고르기 전에 사용자 목표, 작업 빈도, 실패 비용, 정보 위계를 먼저 판단하십시오. 시각적 취향보다 이해 가능성, 행동 예측성, 접근성을 우선하십시오.

## 프로젝트에 연결하기

패키지를 설치한 프로젝트 루트에서 다음 명령을 실행하십시오.

```bash
ln -s node_modules/@opnay/city-ds-react/DESIGN.md ./DESIGN.md
```

프로젝트에 이미 `DESIGN.md`가 있다면 덮어쓰지 말고 기존 지침에서 이 파일을 참조하십시오. 심볼릭 링크를 사용하면 패키지를 업데이트할 때 가이드도 함께 갱신됩니다.

애플리케이션 진입점에서는 앱 기반 스타일을 한 번만 불러오십시오.

```tsx
import '@opnay/city-ds-react/styles.css';
```

전역 리셋이나 컴포넌트 스타일 없이 토큰만 필요하면 `@opnay/city-ds-react/theme.css`를 사용하십시오.

## 결정 순서

화면을 만들거나 수정할 때 다음 순서를 지키십시오.

1. 사용자의 목표, 작업 빈도, 숙련도, 실패 비용을 확인하십시오.
2. 화면을 탐색, 명령, 콘텐츠, 상세, 상태 영역으로 나누고 읽기 순서를 정하십시오.
3. 화면 > 영역 > 그룹 > 요소 순서로 정보와 액션의 위계를 정하십시오.
4. 아래 선택 기준으로 컴포넌트를 고르십시오.
5. 같은 역할의 크기, 밀도, 표면, 톤을 통일하십시오.
6. 기본, 로딩, 빈 상태, 오류, 성공, 비활성, 권한 부족 상태를 설계하십시오.
7. 키보드, 스크린 리더, 긴 문구, 현지화, 작은 화면에서 다시 확인하십시오.

스타일을 먼저 정한 뒤 의미를 끼워 맞추지 마십시오. 기존 컴포넌트와 토큰으로 표현할 수 있다면 새 패턴이나 일회성 크기·색상·그림자를 추가하지 마십시오.

## 위계와 액션

### 위계 범위

| 범위 | 정해야 하는 것                        | 기준                                                                |
| ---- | ------------------------------------- | ------------------------------------------------------------------- |
| 화면 | 제목, 핵심 목표, 주요 액션            | 한 화면에서 무엇을 이해하고 완료해야 하는지 즉시 보여주십시오.      |
| 영역 | 제목, 데이터나 작업의 경계, 영역 액션 | 탐색, 필터, 콘텐츠, 상세, 상태의 역할을 분리하십시오.               |
| 그룹 | 관련 항목, 선택지, 액션 우선순위      | 근접성, 정렬, 간격을 먼저 사용하고 필요할 때만 표면을 추가하십시오. |
| 요소 | 레이블, 값, 상태, 개별 액션           | 부모 그룹이 허용하는 위계 안에서 일관된 표현을 사용하십시오.        |

자식 요소에 더 강한 지속적 강조가 필요하면 크기나 색상을 예외로 키우지 말고 해당 요소가 더 높은 영역에 속해야 하는지 검토하십시오. 오류, 포커스, 선택, 진행 표시는 기능 상태이므로 필요한 가시성을 유지하되 정보 위계를 바꾸는 장식으로 사용하지 마십시오.

### 콘텐츠 타이포그래피

컴포넌트 밖의 제목, 문장과 문단은 의미 HTML과 시각 역할을 분리하십시오. heading 수준은 문서 구조를 따르고 `city-text-*` 클래스는 글꼴, 크기, 행간, 굵기와 자간만 정합니다.

| 역할 클래스                  | 규격                | 대표 용도         |
| ---------------------------- | ------------------- | ----------------- |
| `city-text-display`          | 36–48px / 1         | 대표 메시지       |
| `city-text-page-title`       | 30–36px / 1.1       | 페이지 제목       |
| `city-text-section-title`    | 24 / 32px, semibold | 섹션 제목         |
| `city-text-subsection-title` | 20 / 28px, semibold | 하위 섹션 제목    |
| `city-text-lead`             | 18 / 28px, regular  | 도입 문단         |
| `city-text-body`             | 16 / 24px, regular  | 기본 문장과 문단  |
| `city-text-supporting`       | 14 / 20px, regular  | 보조 설명         |
| `city-text-caption`          | 12 / 16px, regular  | 캡션과 메타데이터 |

여러 문단에는 `city-prose`를 사용하십시오. 이 클래스는 68ch 읽기 폭, 16px 흐름 간격, 제목 전 추가 간격, 목록 들여쓰기와 긴 문자열 줄바꿈만 제공하며 하위 요소의 텍스트 역할은 자동으로 정하지 않습니다.

```tsx
<article className="city-prose">
  <h1 className="city-text-page-title">교통 관제 요약</h1>
  <p className="city-text-lead">오늘의 주요 운영 상태입니다.</p>
  <h2 className="city-text-section-title">운행 상태</h2>
  <p className="city-text-body">일반적인 설명을 여기에 작성합니다.</p>
</article>
```

역할 클래스는 색상과 외부 여백을 포함하지 않습니다. 오류와 필수 안내를 `city-text-caption` 또는 낮은 대비로 약화하지 말고, 색상만으로 정보 위계를 표현하지 마십시오. Button·Input·Badge 같은 컴포넌트 내부 텍스트는 각 컴포넌트와 Control Text 계약을 유지하십시오.

### 버튼 우선순위

한 그룹에는 원칙적으로 하나의 `primary` 액션만 두십시오. 페이지의 주요 액션과 다이얼로그의 주요 액션은 서로 다른 그룹이므로 각각 하나씩 가질 수 있습니다.

| `Button` variant | 사용 상황                                                |
| ---------------- | -------------------------------------------------------- |
| `primary`        | 저장, 생성, 적용처럼 그룹의 목표를 완료하는 대표 액션    |
| `secondary`      | 대표 액션과 함께 자주 쓰는 보조 액션                     |
| `outline`        | 중립적인 대안, 취소, 이전 단계                           |
| `ghost`          | 툴바, 행, 좁은 영역의 낮은 우선순위 액션                 |
| `destructive`    | 삭제, 철회처럼 손실이나 중대한 영향을 일으키는 실행 액션 |

버튼 크기로 우선순위를 표현하지 마십시오. 같은 액션 그룹에서는 같은 크기를 쓰고 variant, 배치, 레이블로 위계를 표현하십시오. 아이콘만 있는 버튼에는 `iconOnly`와 `aria-label` 또는 `aria-labelledby`를 제공하십시오. 링크로 이동하는 액션은 `render`로 실제 링크 요소를 사용하고 `asChild` 패턴을 추가하지 마십시오.

CTA는 결과를 예측할 수 있게 쓰십시오. `확인`, `예`보다 `변경사항 저장`, `멤버 삭제`처럼 행동과 결과를 드러내십시오.

## 크기와 밀도

### 제어 크기

공통 제어 크기는 `sm | md | lg`이고 기본값은 `md`입니다.

| 크기 | 높이 | 사용 상황                                       |
| ---- | ---: | ----------------------------------------------- |
| `sm` | 32px | 반복 행, 조밀한 툴바, 데이터 중심의 보조 제어   |
| `md` | 36px | 일반 폼, 페이지 액션, 기본 선택                 |
| `lg` | 40px | 여유 있는 단일 작업, 낮은 밀도의 주요 입력 영역 |

- 같은 행, 폼 구간, 툴바, 선택 그룹에서는 같은 크기를 사용하십시오.
- `sm`은 위계가 낮다는 뜻이 아니며 `lg`는 더 중요하다는 뜻이 아닙니다.
- 시각 크기와 접근 가능한 입력 영역을 구분하십시오. 포인터가 거친 환경에서는 `--city-hit-target-min`인 44px 이상의 hit target을 보존하십시오.
- `Select`, `Combobox`, `NumberField`, `SearchField`, `RadioGroup`, `CheckboxGroup`, `ToggleGroup`, `Toolbar` 같은 합성 컴포넌트는 Root 크기를 자식에 상속시키고, 실제로 다른 역할인 자식만 명시적으로 재정의하십시오.
- `Badge`, `Progress`, `Skeleton`은 주변 텍스트나 대체할 콘텐츠의 시각 크기에 맞추십시오.

`Dialog`와 `Drawer`의 `sm | md | lg | xl | full`은 액션 위계가 아니라 콘텐츠 폭입니다. 짧은 정보는 `sm`, 일반 폼은 `md`, 여러 구간이나 넓은 비교는 `lg`·`xl`을 사용하십시오. `full`은 넓은 작업 공간이 반드시 필요할 때만 사용하십시오.

### 정보 밀도

기본 밀도는 `comfortable`입니다. 반복 작업과 비교가 중요한 데이터 화면에서만 `compact`를 사용하십시오. 한 영역의 밀도는 `DensityProvider`로 정하고 개별 컴포넌트 override는 의미가 다른 하위 영역에만 사용하십시오.

```tsx
<DensityProvider density="compact">
  <FilterBar>{/* filters */}</FilterBar>
  <Pagination.Root>{/* pages */}</Pagination.Root>
</DensityProvider>
```

`DensityProvider`는 `FilterBar`, `Menu`, `Pagination`, `Tabs`, `FileUpload`에 적용됩니다. `Table`은 `size`, `EmptyState`는 `default | compact` density로 조절하십시오. 작은 화면이라는 이유만으로 무조건 compact를 사용하지 마십시오. 터치 정확도와 읽기 용이성이 더 중요할 수 있습니다.

## 컴포넌트 선택

### 액션과 선택

| 필요                                          | 사용          | 다른 선택을 써야 할 때                                                 |
| --------------------------------------------- | ------------- | ---------------------------------------------------------------------- |
| 즉시 실행하거나 제출하는 명령                 | `Button`      | 켜짐 상태가 유지되면 `Toggle`이나 `Switch`를 사용하십시오.             |
| 보기 모드, 서식처럼 눌림 상태가 유지되는 옵션 | `Toggle`      | 즉시 적용되는 설정값은 `Switch`를 사용하십시오.                        |
| 서로 관련된 단일·복수 토글                    | `ToggleGroup` | 폼의 명시적 값 선택은 `RadioGroup`이나 `CheckboxGroup`을 사용하십시오. |
| 반복 작업의 명령과 토글 묶음                  | `Toolbar`     | 일반적인 페이지 CTA를 담는 장식용 컨테이너로 쓰지 마십시오.            |

`ToggleGroup`과 아이콘 전용 항목에는 각각 접근 가능한 이름을 제공하십시오. 선택 여부를 색상에만 의존하지 말고 눌림 상태, 아이콘, 레이블에서도 알 수 있게 하십시오.

### 폼

| 필요                                     | 사용                        | 선택 기준                                                                  |
| ---------------------------------------- | --------------------------- | -------------------------------------------------------------------------- |
| 레이블, 설명, 오류가 있는 단일 필드      | `Field`                     | 모든 입력에 보이는 레이블을 우선하고 오류에는 원인과 복구 방법을 쓰십시오. |
| 의미가 같은 여러 필드                    | `Fieldset`                  | `Legend`로 그룹 이름을 제공하고 단순 시각 묶음에는 사용하지 마십시오.      |
| 한 줄 자유 텍스트                        | `Input`                     | 여러 줄이면 `Textarea`, 숫자 연산이면 `NumberField`를 사용하십시오.        |
| 접두사, 단위, 인라인 액션이 있는 입력    | `InputGroup`                | 장식 때문에 사용하지 말고 하나의 입력 경계를 공유할 때 사용하십시오.       |
| 여러 줄 텍스트                           | `Textarea`                  | 초기 높이를 예상 분량에 맞추고 세로 resize를 유지하십시오.                 |
| 증감, 범위, 숫자 검증이 필요한 값        | `NumberField`               | 전화번호, 우편번호처럼 계산하지 않는 숫자 문자열은 `Input`을 사용하십시오. |
| 검색어 제출, 지우기, 로딩이 있는 검색    | `SearchField`               | 일반 텍스트 필터는 `Input`, 목록 내 탐색 선택은 `Combobox`를 사용하십시오. |
| 짧고 고정된 단일 선택 목록               | `Select`                    | 옵션을 비교해야 하고 수가 적으면 `RadioGroup`을 사용하십시오.              |
| 검색 가능한 긴·동적·다중 선택 목록       | `Combobox`                  | 단순한 고정 목록에는 `Select`를 우선하십시오.                              |
| 2~5개의 상호 배타적 선택지를 한눈에 비교 | `RadioGroup`                | 공간이 부족하거나 목록이 길면 `Select`를 사용하십시오.                     |
| 독립적인 동의나 복수 선택                | `Checkbox`, `CheckboxGroup` | 즉시 켜고 끄는 설정은 `Switch`를 사용하십시오.                             |
| 저장 버튼 없이 즉시 적용되는 이진 설정   | `Switch`                    | 폼 제출 시 확정되는 선택은 `Checkbox`를 사용하십시오.                      |
| 파일 선택과 선택 목록 제거               | `FileUpload`                | 네트워크 업로드, 재시도, 서버 진행률은 소비자 코드에서 처리하십시오.       |

필수 여부, 형식, 단위, 제한은 입력 전에 알 수 있게 하십시오. 제출 후 오류만 보여주지 말고 가능하면 잘못된 필드 가까이에 원인과 수정 방법을 표시하십시오. 비활성 상태로 이유를 숨기기보다 필요한 조건을 설명하십시오.

### 탐색과 공개

| 필요                              | 사용          | 피해야 할 사용                                                      |
| --------------------------------- | ------------- | ------------------------------------------------------------------- |
| 현재 페이지의 상위 경로           | `Breadcrumbs` | 방문 기록이나 단계 진행을 표현하지 마십시오.                        |
| 같은 맥락의 병렬 콘텐츠 전환      | `Tabs`        | 순서가 있는 절차나 서로 다른 주요 목적을 한 화면에 숨기지 마십시오. |
| 명령, 링크, 체크·라디오 액션 목록 | `Menu`        | 폼 값을 고르는 드롭다운 대신 사용하지 마십시오.                     |
| 큰 결과 집합의 명시적 페이지 이동 | `Pagination`  | 데이터가 적거나 연속 탐색이 더 적합하면 표시하지 마십시오.          |
| 보조 정보를 펼치고 접기           | `Accordion`   | 주요 정보를 기본적으로 숨기거나 페이지 탐색을 대신하지 마십시오.    |

현재 위치, 선택 상태, 돌아갈 경로를 함께 보존하십시오. 긴 breadcrumbs 경로는 의미 있는 중간 항목을 `Ellipsis`로 직접 축약하고 현재 페이지는 링크로 만들지 마십시오.

### 오버레이

| 필요                                  | 사용          | 선택 기준                                                     |
| ------------------------------------- | ------------- | ------------------------------------------------------------- |
| 짧고 비필수적인 설명                  | `Tooltip`     | 핵심 지침, 오류, 상호작용 콘텐츠를 넣지 마십시오.             |
| 현재 요소에 붙는 작은 상호작용·상세   | `Popover`     | 긴 작업이나 여러 필드는 `Dialog`를 사용하십시오.              |
| 현재 화면 위의 집중된 확인·입력·편집  | `Dialog`      | 배경 맥락과 병행해야 하는 상세는 `Drawer`가 적합합니다.       |
| 복구하기 어렵거나 영향이 큰 결정 확인 | `AlertDialog` | 일반 입력이나 쉽게 되돌릴 수 있는 작업에는 사용하지 마십시오. |
| 맥락을 유지하는 탐색·상세·보조 작업   | `Drawer`      | 짧은 확인만 필요하면 `Dialog`나 `Popover`를 사용하십시오.     |

오버레이에는 접근 가능한 제목, 명확한 닫기 경로, 예측 가능한 초기 포커스와 트리거로의 포커스 복귀를 제공하십시오. 긴 `Dialog`는 본문만 스크롤하고 제목과 주요 액션을 유지하십시오. `Drawer`의 `side`와 닫힘 방향을 일치시키십시오. 모바일 bottom sheet는 짧은 선택과 보조 작업에만 사용하십시오.

손실이 작고 되돌릴 수 있는 작업은 `AlertDialog`를 반복해서 띄우기보다 실행 후 Undo를 제공하십시오. 삭제 확인에서는 대상, 결과, 복구 가능 여부를 설명하고 실행 버튼에 구체적인 파괴적 레이블을 사용하십시오.

### 피드백과 상태

| 필요                                     | 사용                   | 지속 시간과 범위                                                          |
| ---------------------------------------- | ---------------------- | ------------------------------------------------------------------------- |
| 짧은 상태, 분류, 개수                    | `Badge`                | 객체나 행 가까이에 두고 문장이나 오류 설명을 대신하지 마십시오.           |
| 페이지 안에 유지되는 정보·성공·경고·오류 | `Alert` 또는 `Callout` | 관련 영역 가까이에 원인, 영향, 다음 행동을 표시하십시오.                  |
| 작업 후 일시적인 전역 결과               | `Toast`                | 사용자가 나중에 다시 봐야 하는 정보에는 사용하지 마십시오.                |
| 콘텐츠가 없는 이유와 다음 행동           | `EmptyState`           | 제목, 짧은 설명, 가능한 대표 액션을 제공하십시오.                         |
| 구조를 예측할 수 있는 초기 로딩          | `Skeleton`             | 실제 콘텐츠의 수와 형태를 닮게 하고 상위 영역에 로딩 이름을 제공하십시오. |
| 측정 가능한 처리 진행 또는 대기          | `Progress`             | 값이 있으면 determinate, 알 수 없으면 indeterminate로 표현하십시오.       |

톤은 `neutral | info | success | warning | destructive` 의미를 일관되게 유지하십시오. 색상만으로 상태를 전달하지 말고 아이콘, 제목, 설명, 위치를 함께 사용하십시오. `warning`은 주의 후 진행할 수 있는 상태, `destructive`는 실패나 손실 위험에 사용하십시오.

클릭이나 입력에는 즉시 반응하고, 지연 작업에는 진행 중인 이유를 보여주십시오. 완료, 실패, 취소, 부분 성공을 구분하고 각각 다음 행동을 제공하십시오. Toast가 사라져도 중요한 오류와 복구 경로는 관련 영역에 남아야 합니다.

### 데이터와 레이아웃

| 필요                             | 사용              | 기준                                                                         |
| -------------------------------- | ----------------- | ---------------------------------------------------------------------------- |
| 행과 열을 비교하는 구조화 데이터 | `Table`           | 열 제목, 단위, 정렬 방향, 선택 이름, 빈·로딩 행을 제공하십시오.              |
| 가로 스크롤 가능한 테이블 영역   | `DataTableRegion` | 고유한 `label`과 작은 화면의 스크롤 힌트를 제공하십시오.                     |
| 필터 제어와 적용·초기화 액션     | `FilterBar`       | 필터와 결과의 관계가 보이게 하고 좁은 화면에서는 흐름 순서로 재배치하십시오. |

비교가 핵심이면 필요한 열을 한눈에 볼 수 있는 밀도를 유지하십시오. 모바일에서 표를 무조건 카드 목록으로 바꾸지 말고 비교 가치, 열 우선순위, 가로 스크롤 중 적합한 방식을 선택하십시오. 로딩 중 기존 데이터를 모두 지워 문맥을 잃게 하지 말고 갱신 상태를 구분하십시오.

## 표면, 색상, 타이포그래피

`plain | band | outline`은 장식이 아니라 그룹 경계를 표현하는 표면입니다.

- `plain`: 주변 레이아웃의 간격과 정렬만으로 관계가 충분할 때 사용하십시오.
- `band`: 툴바나 필터처럼 페이지 폭의 기능 영역을 배경으로 구분할 때 사용하십시오.
- `outline`: 독립적인 경계와 상호작용 영역이 필요할 때 사용하십시오.

부모와 자식에 같은 테두리, radius, 그림자를 반복하지 마십시오. 내부 그룹은 먼저 간격, 정렬, 제목, divider로 구분하십시오. 카드나 패널은 독립된 정보, 액션, 상태를 소유할 때만 추가하십시오.

색상, 간격, 글꼴, radius, 그림자, 모션은 `--city-*` 토큰을 사용하십시오. 브랜드 색을 추가하더라도 action, status, destructive 의미와 충돌시키지 마십시오. 라이트, 다크, 시스템 테마에서 같은 의미와 대비를 유지하고 상태를 색상 하나에만 맡기지 마십시오.

제목 수준은 문서 구조를 따르십시오. 글자 크기로 heading 순서를 흉내 내지 마십시오. 보조 텍스트는 낮은 대비를 사용할 수 있지만 읽을 수 있어야 하며, 오류나 필수 지침을 보조 장식처럼 약하게 만들지 마십시오.

## 반응형과 콘텐츠

- DOM과 키보드의 읽기 순서를 먼저 올바르게 만들고 CSS로 재배치하십시오.
- 작은 화면에서는 보조 액션을 다음 줄이나 Menu로 이동하되 주요 액션은 찾을 수 있게 유지하십시오.
- 긴 레이블과 현지화 문구는 줄바꿈, 영역 확장, 공통 반응형 규칙으로 처리하십시오. 한 요소만 글자를 줄여 맞추지 마십시오.
- 오버레이와 팝업이 viewport 밖으로 나가지 않게 하고 긴 본문은 적절한 내부 영역에서 스크롤하십시오.
- hover 없이도 모든 행동을 발견하고 실행할 수 있게 하십시오.
- 로딩, 오류, 선택, 포커스, disabled 상태는 라이트·다크 테마와 키보드에서 확인하십시오.

## 접근성과 상태 점검

Base UI가 제공하는 키보드, 포커스, ARIA, 상태 동작을 재구현하지 마십시오. 합성 API는 `render`를 사용하십시오.

- 모든 폼 제어, 아이콘 버튼, ToggleGroup, Toolbar, table region에 접근 가능한 이름이 있습니까?
- heading 순서와 landmark가 시각 배치와 같은 문서 구조를 표현합니까?
- Tab, Shift+Tab, 방향키, Enter, Space, Escape로 흐름을 완료하고 닫은 뒤 돌아올 수 있습니까?
- focus ring이 모든 표면과 테마에서 보입니까?
- 오류는 원인, 영향, 복구 방법을 설명하고 해당 필드나 영역과 연결됩니까?
- loading, empty, error, success, disabled, permission 상태에서 다음 행동이 분명합니까?
- 터치 대상, 대비, 읽기 순서, 애니메이션이 접근성을 약화시키지 않습니까?

## 조합 예시

### 데이터 관리 화면

`Breadcrumbs` > 페이지 제목과 대표 `Button` > `FilterBar` > `DataTableRegion` 안의 `Table` > `Pagination` 순서로 구성하십시오. 행 상세는 `Drawer`, 편집은 `Dialog`, 복구하기 어려운 삭제는 `AlertDialog`, 짧은 저장 결과는 `Toast`를 사용하십시오.

### 설정 폼

관련 설정을 `Fieldset`으로 묶고 각 입력은 `Field`로 설명과 오류를 연결하십시오. 즉시 적용되는 이진 설정은 `Switch`, 제출 시 확정되는 복수 선택은 `CheckboxGroup`, 짧은 단일 선택은 `RadioGroup`을 사용하십시오. 폼 끝에는 같은 크기의 보조 버튼과 하나의 `primary` 저장 버튼을 두십시오.

## 최종 품질 기준

동일한 역할·위계·상태에는 동일한 컴포넌트, 크기, 밀도, 톤, 표면을 적용하십시오. 예외가 필요하면 콘텐츠 길이, 상호작용, 위험, 반응형 같은 반복 가능한 의미 차이로 설명할 수 있어야 합니다. 정상 경로만 완성하지 말고 지연, 빈 상태, 실패, 권한 상실, 긴 콘텐츠, 키보드, 작은 화면에서도 사용자가 목표를 완료하거나 안전하게 복구할 수 있게 하십시오.
