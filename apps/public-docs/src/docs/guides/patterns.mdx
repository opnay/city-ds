## 프로젝트 패턴 계층을 구축하십시오

city-ds는 범용 기초·컴포넌트·공통 디자인 계약을 제공합니다. 각 프로젝트는 이를 실제 사용자
목표와 업무 흐름에 맞는 추가 패턴으로 구성해야 합니다. 개별 컴포넌트를 페이지에서 직접
조립하는 방식만 반복하면 도메인 위계, 상태, 간격과 반응형 규칙이 페이지마다 달라집니다.

`사용자 목표 > 프로젝트 패턴 선택·정의 > 컴포넌트 구성 > 레이아웃 구성 > 페이지 구현`
순서를 지키십시오.

| 단계                    | 정의할 계약                                                                  | 대표 산출물                      |
| ----------------------- | ---------------------------------------------------------------------------- | -------------------------------- |
| 사용자 목표             | 사용자, 핵심 작업, 빈도, 실패 비용, 완료와 실패 조건                         | 제품 판단 기준                   |
| 프로젝트 패턴 선택·정의 | 기존 패턴 재사용 여부, 이름, 적용·비적용 조건, 필수 상태와 필요한 구성·배치  | 선택하거나 새로 정의한 패턴 명세 |
| 컴포넌트 구성           | 도메인 역할, 컴포넌트 조합, variant·size·density, 상태와 접근성 이름         | 필터 묶음, 데이터 영역, 폼 구간  |
| 레이아웃 구성           | Page > Section > Region > Component 위계, spacing·surface·반응형과 읽기 순서 | 프로젝트 레이아웃 패턴           |
| 페이지 구현             | 실제 데이터, 라우팅, 권한, 액션, 피드백, 부수 효과와 복구 흐름               | 동작하는 제품 화면               |

프로젝트 패턴에는 이름, 사용자 목표, 적용·비적용 조건, 컴포넌트 구성, 레이아웃 규칙, 필수 상태,
부수 효과 소유자와 완료 기준을 기록하십시오. 동일한 역할의 화면은 같은 패턴을 사용하고 예외는
콘텐츠 길이, 위험, 권한, 상호작용이나 viewport처럼 반복 가능한 이유로 설명할 수 있어야 합니다.

모든 컴포넌트를 wrapper로 감싸거나 일회성 배치를 억지로 공통화하지 마십시오. 프로젝트의
도메인 정책은 해당 프로젝트가 소유하고, 여러 프로젝트에서 같은 의미와 변경 이유로 반복될
때만 city-ds 패턴이나 컴포넌트로 승격을 검토하십시오.

## 간격은 역할에 따라 나누십시오

간격 값은 같은 `--city-space-*` scale을 사용하되 책임은 Component Spacing과 Layout Spacing으로
구분하십시오. Component Spacing은 카드·필드 그룹·툴바·리스트 내부의 관계를 소유하고
density에 반응합니다. Layout Spacing은 page gutter·section gap·grid gutter를 소유하고
viewport와 정보 구조에 반응합니다.

### Component Spacing

| 관계               | Comfortable | Compact | 대표 용도                  |
| ------------------ | ----------- | ------- | -------------------------- |
| Item               | 12px        | 8px     | 필드, 반복 행, 관련 요소   |
| Group              | 16px        | 12px    | 필드 묶음, 툴바, 카드 구간 |
| Container          | 16px        | 12px    | 카드·패널의 기본 padding   |
| Spacious Container | 24px        | —       | 저밀도 단일 작업과 안내    |

2·4·6·10·14px는 indicator, title–meta, control 내부 정렬 같은 미세 조정에만 사용하십시오.
Container와 영역 배치에는 8·12·16·24px 단계를 우선하십시오.

### Layout Spacing

| 역할        | Mobile  | Medium  | Desktop | 소유자       |
| ----------- | ------- | ------- | ------- | ------------ |
| Page gutter | 16px    | 20px    | 32px    | Page shell   |
| Section gap | 32px    | 40px    | 48px    | Page content |
| Region gap  | 24px    | 24–32px | 32px    | Section      |
| Grid gutter | 12–16px | 16px    | 16–24px | Grid         |
| Page end    | 48px    | 48px    | 64px    | Page shell   |

값은 기본 시작점입니다. 정보 구조나 작업 공간의 성격이 다르면 같은 scale 안에서 조정할 수
있지만, 같은 경계를 인접한 부모와 자식이 나눠 소유하지 마십시오.

- 부모가 자식 사이의 `gap`과 자신의 `padding`을 소유합니다.
- 같은 surface의 header·body·footer는 동일한 inline gutter를 사용합니다.
- Page > Section > Region > Component 경계마다 spacing 소유자를 하나만 둡니다.
- breakpoint에서는 Layout Spacing만 바꾸고 component density와 control size는 유지합니다.
- 빈 상태의 위치는 container가 정렬하며 자식의 임의 margin으로 보정하지 않습니다.
- `margin-top: auto`는 동일 높이 카드의 action처럼 명시적인 끝 정렬에만 사용합니다.

`DensityProvider` 적용 범위와 전체 토큰 사용법은 [기초 문서](/foundations)를 참고하십시오.

## 폼은 의미 단위로 합성하십시오

각 입력에는 보이는 레이블, 필요한 설명, 복구 방법이 담긴 오류를 제공하십시오.
`Field`는 하나의 control을, `Fieldset`은 같은 의미의 여러 control을 묶습니다.
입력에만 placeholder를 두고 레이블을 생략하지 마십시오.

| 제어                                                  | 폼 문맥과 Label                   |
| ----------------------------------------------------- | --------------------------------- |
| Input, Textarea, NumberInput, SearchInput, DatePicker | 외부 `Field.Root`와 `Field.Label` |
| 입력형 Combobox                                       | 외부 `Field.Root`와 `Field.Label` |
| 단독 Select                                           | `Select.Label`                    |
| Trigger형 Combobox                                    | `Combobox.Label`                  |

입력 컴포넌트와 DatePicker는 값을 입력하거나 선택하는 제어만 소유합니다.
레이블, 설명, 오류, 폼 상태는 외부 `Field`에서 일관되게 구성하십시오.
합성 입력의 `disabled`와 `invalid` 상태는 `Field.Root`와 입력 Root에 동일하게 전달하십시오.

```tsx
import { Field } from '@opnay/city-ds-react/field';
import { Input } from '@opnay/city-ds-react/input';

<Field.Root invalid>
  <Field.Label>작업 공간 이름</Field.Label>
  <Input defaultValue="a" />
  <Field.Description>3자 이상 입력하십시오.</Field.Description>
  <Field.Error match>작업 공간 이름은 3자 이상이어야 합니다.</Field.Error>
</Field.Root>;
```

고정된 짧은 단일 선택은 `Select`, 비교가 중요한 적은 선택지는 `RadioGroup`, 검색·긴
목록·다중 선택은 `Combobox`를 사용하십시오. 검색을 제출하거나 지우는 흐름은
`SearchInput`에 두고, 단순 텍스트 필터에는 `Input`으로 충분한지 먼저 확인하십시오.

## 피드백은 지속 시간과 다음 행동으로 고르십시오

| 상황                                       | 선택         | 기준                                            |
| ------------------------------------------ | ------------ | ----------------------------------------------- |
| 현재 화면에서 바로 읽고 해결해야 하는 상태 | `Alert`      | 제목, 설명, 복구 action을 화면 안에 유지        |
| 데이터가 아직 없고 다음 행동이 필요한 영역 | `EmptyState` | 빈 이유와 생성·필터 해제 action 제시            |
| 진행 중인 작업                             | `Progress`   | 결정 가능한 진행률 또는 indeterminate 상태 표시 |
| 짧게 확인해도 되는 완료·실패 결과          | `Toast`      | 현재 작업을 가리지 않되 action이 있으면 유지    |
| 콘텐츠 자리를 유지하는 로딩                | `Skeleton`   | 실제 구조와 가까운 크기로 사용                  |

`Alert`의 오류는 색상만으로 전달하지 말고 제목, 설명, 아이콘 또는 상태 텍스트도 함께
제공하십시오.

## 오버레이는 작업의 범위로 고르십시오

| 필요                                      | 선택          | 피해야 할 선택                           |
| ----------------------------------------- | ------------- | ---------------------------------------- |
| 짧은 보조 설명                            | `Tooltip`     | 필수 지침과 오류를 tooltip에만 두는 방식 |
| 트리거 주변의 작은 선택·추가 정보         | `Popover`     | 긴 편집 흐름이나 복잡한 확인             |
| 집중이 필요한 편집·세부 작업              | `Dialog`      | 단순한 문맥 설명                         |
| 화면 가장자리에서 이어지는 상세·보조 작업 | `Drawer`      | 되돌리기 어려운 확인                     |
| 삭제·철회처럼 복구하기 어려운 결정        | `AlertDialog` | 일반 알림 또는 Toast                     |

overlay 안에는 명확한 제목과 닫기 방법을 제공하고, action의 결과가 무엇인지 레이블에
적으십시오. 열린 상태와 포커스 이동은 제공된 Trigger, Popup, Close 계약에 맡기고
별도의 document 이벤트로 다시 구현하지 마십시오.

## 링크는 링크로 렌더링하십시오

이동 행동이 버튼 모양을 가져야 하면 `render`에 실제 링크를 합성하십시오. `asChild`를
추가하지 마십시오. 아래 예시는 TanStack Router를 사용하는 앱의 내부 링크입니다.

```tsx
import { Link } from '@tanstack/react-router';
import { Button } from '@opnay/city-ds-react/button';

<Button nativeButton={false} render={<Link to="/projects" />} role="link" variant="outline">
  프로젝트로 이동
</Button>;
```

이 방식은 주소 복사, 새 탭 열기, 보조 기술의 링크 역할을 보존합니다. 명령을 실행하는
행동은 `button`, 경로를 바꾸는 행동은 `Link` 또는 앵커로 남기십시오.

## 데이터 목록은 좁은 화면을 포함해 설계하십시오

목록의 탐색 순서는 보통 Breadcrumbs, 제목과 대표 action, `FilterBar`, `DataTableRegion`
안의 `Table`, `Pagination`입니다. Table은 행과 열의 비교에 쓰고, 카드로 바꿔야 할
이유가 있는지 작은 화면에서 먼저 확인하십시오.

```tsx
import { DataTableRegion } from '@opnay/city-ds-react/data-table-region';
import { Table } from '@opnay/city-ds-react/table';

<DataTableRegion hint="표를 가로로 스크롤하면 모든 열을 확인할 수 있습니다." label="프로젝트 목록">
  <Table.Root>{/* Header, Body, Row, Cell */}</Table.Root>
</DataTableRegion>;
```

`DataTableRegion`에는 고유한 `label`을 주고, 좁은 화면에서 가로 스크롤 가능하다는
힌트를 제공하십시오. 로딩, 빈 결과, 오류, overflow 상태도 기본 목록과 함께 확인해야
합니다.

`FilterBar`와 Table을 한 데이터 영역에 배치할 때는 첫·마지막 열의 16px inline gutter를
필터 콘텐츠의 바깥 정렬선과 맞추십시오. Table의 `size`는 셀 내부 밀도만 바꾸며 영역의
바깥 정렬선은 바꾸지 않습니다.

`table-layout: fixed`를 사용한다면 짧은 상태·숫자·날짜·액션 열에는 실제 콘텐츠가 들어갈
최소 너비를 지정하고, 주요 텍스트 열만 남은 폭을 사용하게 하십시오. `nowrap` 콘텐츠가
인접 열을 침범하게 두거나 중요한 값을 잘라 맞추지 말고, 전체 최소 너비가 화면을 넘으면
`DataTableRegion`의 가로 스크롤을 유지하십시오.
