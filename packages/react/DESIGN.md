# @opnay/city-ds-react 디자인 가이드

이 문서는 `@opnay/city-ds-react` 디자인 시스템을 이용한 웹 어플리케이션 및 웹 사이트 제작 기준입니다. 사람과 코드 에이전트 모두 컴포넌트를 고르기 전에 사용자 목표, 작업 빈도, 실패 비용, 정보 위계를 먼저 판단하십시오. 시각적 취향보다 이해 가능성, 행동 예측성, 접근성을 우선하십시오.

## 프로젝트에 연결하기

패키지를 설치한 프로젝트 루트에서 다음 명령을 실행하십시오.

```bash
ln -s node_modules/@opnay/city-ds-react/DESIGN.md ./DESIGN.md
```

프로젝트에 이미 `DESIGN.md`가 있다면 덮어쓰지 말고 기존 지침에서 이 파일을 참조하십시오. 심볼릭 링크를 사용하면 패키지를 업데이트할 때 가이드도 함께 갱신됩니다.

애플리케이션 진입점에서는 앱 기반 스타일을 한 번만 불러오십시오.

```tsx
import '@opnay/city-ds-react/styles.css';
```

전역 리셋이나 컴포넌트 스타일 없이 토큰만 필요하면 `@opnay/city-ds-react/theme.css`를 사용하십시오.

## 프로젝트 패턴 계층

city-ds를 사용하는 프로젝트는 개별 컴포넌트를 페이지에서 직접 조립하는 방식에 머물지 마십시오. 반복되는 업무 흐름은 프로젝트의 사용자, 정보 구조, 작업 빈도, 위험, viewport에 맞는 프로젝트 패턴으로 정의하고 사용하십시오.

사용자 목표를 먼저 확인한 뒤 기존 프로젝트 패턴을 선택하거나 새 패턴을 정의하십시오. 프로젝트 패턴은 적용 조건, 필수 상태, 컴포넌트 구성과 레이아웃 구성의 계약을 정합니다. 페이지는 이 계약에 실제 데이터와 제품 동작을 연결하는 소비자입니다.

### 구현 순서

`사용자 목표 > 프로젝트 패턴 선택·정의 > 컴포넌트 구성 > 레이아웃 구성 > 페이지 구현` 순서를 지키십시오.

| 단계                    | 프로젝트가 정해야 하는 것                                                                | 결과                               |
| ----------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------- |
| 사용자 목표             | 사용자, 핵심 작업, 빈도, 실패 비용, 완료와 실패 조건                                     | 제품 판단 기준                     |
| 프로젝트 패턴 선택·정의 | 기존 패턴 재사용 여부, 이름, 적용·비적용 조건, 필수 상태와 필요한 구성·레이아웃 계약     | 선택하거나 새로 정의한 패턴 명세   |
| 컴포넌트 구성           | city-ds 컴포넌트의 도메인 역할, 조합, 크기, 밀도, 상태와 접근성 이름                     | 반복 가능한 작업·정보 구성 단위    |
| 레이아웃 구성           | Page > Section > Region > Component 위계, 간격, 정렬, surface, 반응형 재배치와 읽기 순서 | 이름을 가진 프로젝트 레이아웃 패턴 |
| 페이지 구현             | 실제 데이터, 라우팅, 권한, 액션, 피드백, 부수 효과와 복구 흐름                           | 제품에서 동작하는 화면             |

각 프로젝트 패턴에는 다음 계약을 기록하십시오.

- 패턴 이름, 사용자 목표, 적용 조건과 사용하지 않는 조건
- 사용하는 컴포넌트 구성과 허용하는 variant·size·density
- 레이아웃 위계, spacing 소유자, surface와 반응형 규칙
- 기본, 로딩, 빈 상태, 오류, 성공, 비활성, 권한 부족 상태
- 데이터·라우팅·권한·네트워크 작업의 소유자와 실패 복구 방법
- 키보드, 긴 콘텐츠, 작은 화면에서 확인할 수 있는 완료 기준

모든 컴포넌트를 별도 wrapper로 감싸거나 한 번만 쓰는 배치를 억지로 공통화하지 마십시오. 한 프로젝트의 도메인 정책은 해당 프로젝트에 유지하고, 여러 프로젝트에서 같은 의미와 변경 이유로 반복될 때만 city-ds 패턴이나 컴포넌트로 승격을 검토하십시오.

## 결정 순서

화면을 만들거나 수정할 때 다음 순서를 지키십시오.

1. 사용자의 목표, 작업 빈도, 숙련도, 실패 비용을 확인하십시오.
2. 목표와 적용 조건에 맞는 기존 프로젝트 패턴을 선택하거나 새 패턴을 정의하십시오.
3. 패턴을 탐색, 명령, 콘텐츠, 상세, 상태 영역으로 나누고 읽기 순서를 정하십시오.
4. 화면 > 영역 > 그룹 > 요소 순서로 정보와 액션의 위계를 정하십시오.
5. 아래 선택 기준으로 도메인 역할에 맞는 컴포넌트 구성을 만드십시오.
6. 프로젝트의 정보 구조와 환경에 맞는 레이아웃 구성을 정의하십시오.
7. 선택·정의한 패턴에 컴포넌트 구성과 레이아웃 구성을 기록한 뒤 페이지를 구현하십시오.
8. 같은 역할의 크기, 밀도, 표면, 톤을 통일하십시오.
9. 기본, 로딩, 빈 상태, 오류, 성공, 비활성, 권한 부족 상태를 설계하십시오.
10. 키보드, 스크린 리더, 긴 문구, 현지화, 작은 화면에서 다시 확인하십시오.

스타일을 먼저 정한 뒤 의미를 끼워 맞추지 마십시오. 반복되는 흐름에 기존 프로젝트 패턴이 없다면 새 패턴을 정의하십시오. 기존 프로젝트 패턴과 city-ds 컴포넌트·토큰으로 표현할 수 있다면 같은 역할의 패턴이나 일회성 크기·색상·그림자를 다시 만들지 마십시오.

## 위계와 액션

### 위계 범위

| 범위 | 정해야 하는 것                        | 기준                                                                |
| ---- | ------------------------------------- | ------------------------------------------------------------------- |
| 화면 | 제목, 핵심 목표, 주요 액션            | 한 화면에서 무엇을 이해하고 완료해야 하는지 즉시 보여주십시오.      |
| 영역 | 제목, 데이터나 작업의 경계, 영역 액션 | 탐색, 필터, 콘텐츠, 상세, 상태의 역할을 분리하십시오.               |
| 그룹 | 관련 항목, 선택지, 액션 우선순위      | 근접성, 정렬, 간격을 먼저 사용하고 필요할 때만 표면을 추가하십시오. |
| 요소 | 레이블, 값, 상태, 개별 액션           | 부모 그룹이 허용하는 위계 안에서 일관된 표현을 사용하십시오.        |

자식 요소에 더 강한 지속적 강조가 필요하면 크기나 색상을 예외로 키우지 말고 해당 요소가 더 높은 영역에 속해야 하는지 검토하십시오. 오류, 포커스, 선택, 진행 표시는 기능 상태이므로 필요한 가시성을 유지하되 정보 위계를 바꾸는 장식으로 사용하지 마십시오.

### 콘텐츠 타이포그래피

컴포넌트 밖의 제목, 문장과 문단은 의미 HTML과 시각 역할을 분리하십시오. heading 수준은 문서 구조를 따르고 `city-text-*` 클래스는 글꼴, 크기, 행간, 굵기와 자간만 정합니다.

| 역할 클래스                  | 규격                           | 대표 용도         |
| ---------------------------- | ------------------------------ | ----------------- |
| `city-text-display`          | 36–48px / 1                    | 대표 메시지       |
| `city-text-page-title`       | 30–36px / 1.1                  | 페이지 제목       |
| `city-text-section-title`    | 24px / 2rem(32px), semibold    | 섹션 제목         |
| `city-text-subsection-title` | 20px / 1.75rem(28px), semibold | 하위 섹션 제목    |
| `city-text-lead`             | 18px / 1.75rem(28px), regular  | 도입 문단         |
| `city-text-body`             | 16px / 1.75rem(28px), regular  | 기본 문장과 문단  |
| `city-text-supporting`       | 14px / 1.25rem(20px), regular  | 보조 설명         |
| `city-text-caption`          | 12px / 1rem(16px), regular     | 캡션과 메타데이터 |

`city-text-body`의 1.75rem 행간은 한글과 영문에 동일하게 적용하십시오. 언어에 따라 별도 행간을 만들지 마십시오.

여러 문단에는 `city-prose`를 사용하십시오. 이 클래스는 68ch 읽기 폭, 20px 흐름 간격, `h1`–`h6` 앞 24px 추가 간격, 목록 들여쓰기와 긴 문자열 줄바꿈만 제공하며 하위 요소의 텍스트 역할은 자동으로 정하지 않습니다.

```tsx
<article className="city-prose">
  <h1 className="city-text-page-title">교통 관제 요약</h1>
  <p className="city-text-lead">오늘의 주요 운영 상태입니다.</p>
  <h2 className="city-text-section-title">운행 상태</h2>
  <p className="city-text-body">일반적인 설명을 여기에 작성합니다.</p>
</article>
```

역할 클래스는 색상과 외부 여백을 포함하지 않습니다. 오류와 필수 안내를 `city-text-caption` 또는 낮은 대비로 약화하지 말고, 색상만으로 정보 위계를 표현하지 마십시오. Button·Input·Badge 같은 컴포넌트 내부 텍스트는 각 컴포넌트와 Control Text 계약을 유지하십시오.

### 버튼 우선순위

한 그룹에는 원칙적으로 하나의 `primary` 액션만 두십시오. 페이지의 주요 액션과 다이얼로그의 주요 액션은 서로 다른 그룹이므로 각각 하나씩 가질 수 있습니다.

| `Button` variant | 사용 상황                                                |
| ---------------- | -------------------------------------------------------- |
| `primary`        | 저장, 생성, 적용처럼 그룹의 목표를 완료하는 대표 액션    |
| `secondary`      | 대표 액션과 함께 자주 쓰는 보조 액션                     |
| `outline`        | 중립적인 대안, 취소, 이전 단계                           |
| `ghost`          | 툴바, 행, 좁은 영역의 낮은 우선순위 액션                 |
| `destructive`    | 삭제, 철회처럼 손실이나 중대한 영향을 일으키는 실행 액션 |

버튼 크기로 우선순위를 표현하지 마십시오. 같은 액션 그룹에서는 같은 크기를 쓰고 variant, 배치, 레이블로 위계를 표현하십시오. 아이콘만 있는 버튼에는 `iconOnly`와 `aria-label` 또는 `aria-labelledby`를 제공하십시오. 링크로 이동하는 액션은 `render`로 실제 링크 요소를 사용하고 `asChild` 패턴을 추가하지 마십시오.

CTA는 결과를 예측할 수 있게 쓰십시오. `확인`, `예`보다 `변경사항 저장`, `멤버 삭제`처럼 행동과 결과를 드러내십시오.

## 크기와 밀도

### 제어 크기

공통 제어 크기는 `xsm | sm | md | lg | xlg`이고 기본값은 `md`입니다.

| 크기  | 높이 | 사용 상황                         |
| ----- | ---: | --------------------------------- |
| `xsm` | 24px | 매우 조밀한 보조 영역의 짧은 제어 |
| `sm`  | 28px | 반복 행과 조밀한 툴바             |
| `md`  | 32px | 일반 폼과 기본 페이지 액션        |
| `lg`  | 36px | 여유가 필요한 폼과 단일 작업      |
| `xlg` | 40px | 낮은 밀도 화면과 긴 입력          |

- 같은 행, 폼 구간, 툴바, 선택 그룹에서는 같은 크기를 사용하십시오.
- 작은 크기는 위계가 낮다는 뜻이 아니며 큰 크기는 더 중요하다는 뜻이 아닙니다.
- 시각 크기와 접근 가능한 입력 영역을 구분하십시오. 포인터가 거친 환경에서는 `--city-hit-target-min`인 44px 이상의 hit target을 보존하십시오.
- `Select`, `Combobox`, `NumberInput`, `SearchInput`, `RadioGroup`, `CheckboxGroup`, `ToggleGroup`, `Toolbar` 같은 합성 컴포넌트는 Root 크기를 자식에 상속시키고, 실제로 다른 역할인 자식만 명시적으로 재정의하십시오.
- `Badge`, `Progress`, `Skeleton`은 주변 텍스트나 대체할 콘텐츠의 시각 크기에 맞추십시오.

`Dialog`와 `Drawer`의 `sm | md | lg | xl | full`은 액션 위계가 아니라 콘텐츠 폭입니다. 짧은 정보는 `sm`, 일반 폼은 `md`, 여러 구간이나 넓은 비교는 `lg`·`xl`을 사용하십시오. `full`은 넓은 작업 공간이 반드시 필요할 때만 사용하십시오.

### 정보 밀도

기본 밀도는 `comfortable`입니다. 반복 작업과 비교가 중요한 데이터 화면에서만 `compact`를 사용하십시오. 한 영역의 밀도는 `DensityProvider`로 정하고 개별 컴포넌트 override는 의미가 다른 하위 영역에만 사용하십시오.

```tsx
<DensityProvider density="compact">
  <FilterBar>{/* filters */}</FilterBar>
  <Pagination.Root>{/* pages */}</Pagination.Root>
</DensityProvider>
```

`DensityProvider`는 `FilterBar`, `Menu`, `Pagination`, `Tabs`, `FileUpload`에 적용됩니다. `Table`은 `size`, `EmptyState`는 `default | compact` density로 조절하십시오. 작은 화면이라는 이유만으로 무조건 compact를 사용하지 마십시오. 터치 정확도와 읽기 용이성이 더 중요할 수 있습니다.

### 간격 계약

간격은 `Component Spacing`과 `Layout Spacing`으로 구분하십시오. Component Spacing은 카드, 필드 그룹, 툴바, 리스트 안의 padding과 gap을 소유하며 `comfortable | compact` density에 반응합니다. Layout Spacing은 page gutter, section gap, grid gutter를 소유하며 viewport와 정보 구조에 반응합니다.

- 부모가 자식 사이의 `gap`과 자신의 `padding`을 소유하고 자식은 외부 margin을 만들지 마십시오.
- 같은 surface의 header·body·footer는 동일한 inline gutter를 사용하십시오.
- Page > Section > Region > Component 경계마다 spacing 소유자를 하나만 두십시오.
- 부모와 자식이 같은 경계의 padding이나 margin을 동시에 더하지 마십시오.
- breakpoint는 Layout Spacing만 바꾸며 Control Size와 Component Spacing을 암묵적으로 바꾸지 않습니다.

세부 계약과 비교 표본은 Storybook의 `디자인 패턴/Density/Component Spacing`, `디자인 패턴/Layout/Layout Spacing`을 참고하십시오.

## 컴포넌트 선택

### 액션과 선택

| 필요                                | 사용               | 다른 선택을 써야 할 때                                                 |
| ----------------------------------- | ------------------ | ---------------------------------------------------------------------- |
| 즉시 실행하거나 제출하는 명령       | `Button`           | 상태가 유지되는 이진 설정은 `Switch`를 사용하십시오.                   |
| 보기·기간처럼 항상 하나인 짧은 선택 | `SegmentedControl` | 선택과 콘텐츠 패널이 일대일로 연결되면 `Tabs`를 사용하십시오.          |
| 해제 가능한 단일·복수 도구 상태     | `ToggleGroup`      | 폼의 명시적 값 선택은 `RadioGroup`이나 `CheckboxGroup`을 사용하십시오. |
| 반복 작업의 명령과 토글 묶음        | `Toolbar`          | 일반적인 페이지 CTA를 담는 장식용 컨테이너로 쓰지 마십시오.            |

`ToggleGroup`과 아이콘 전용 항목에는 각각 접근 가능한 이름을 제공하십시오. 선택 여부를 색상에만 의존하지 말고 눌림 상태, 아이콘, 레이블에서도 알 수 있게 하십시오.

### 폼

| 레이블, 설명, 오류가 있는 단일 필드      | `Field`                     | 모든 입력에 보이는 레이블을 우선하고 오류에는 원인과 복구 방법을 쓰십시오. |

| 한 줄 자유 텍스트                        | `Input`                     | 여러 줄이면 `Textarea`, 숫자 연산이면 `NumberInput`를 사용하십시오.        |

| 짧고 고정된 단일 선택 목록               | `Select`                    | 옵션을 비교해야 하고 수가 적으면 `RadioGroup`을 사용하십시오.              |
| 검색 가능한 긴·동적·다중 선택 목록       | `Combobox`                  | 단순한 고정 목록에는 `Select`를 우선하십시오.                              |
| 2~5개의 상호 배타적 선택지를 한눈에 비교 | `RadioGroup`                | 공간이 부족하거나 목록이 길면 `Select`를 사용하십시오.                     |
| 독립적인 동의나 복수 선택                | `Checkbox`, `CheckboxGroup` | 즉시 켜고 끄는 설정은 `Switch`를 사용하십시오.                             |
| 저장 버튼 없이 즉시 적용되는 이진 설정   | `Switch`                    | 폼 제출 시 확정되는 선택은 `Checkbox`를 사용하십시오.                      |
| 파일 선택과 선택 목록 제거               | `FileUpload`                | 네트워크 업로드, 재시도, 서버 진행률은 소비자 코드에서 처리하십시오.       |

`Input`, `NumberInput`, `SearchInput`과 `DatePicker`는 입력·선택 제어만 소유합니다. 레이블, 설명, 오류가 필요한 경우 외부 `Field.Root` 안에서 `Field.Label`, 제어, `Field.Description`, `Field.Error`를 조합하십시오. 합성 입력의 `disabled`와 `invalid` 상태는 `Field.Root`와 입력 Root에 동일하게 전달하십시오.

`SearchInput.Root`는 기본적으로 `div`를 렌더합니다. 검색 제출이 필요하면 소비처의 `<form onSubmit={...}>` 안에 배치하고, 값은 `onValueChange` 또는 이름을 지정한 입력의 `FormData`로 읽으십시오. `SearchInput.Submit`은 해당 소비처 form을 제출합니다. Form과 서버 오류 처리 정책은 소비처가 소유합니다.

필수 여부, 형식, 단위, 제한은 입력 전에 알 수 있게 하십시오. 제출 후 오류만 보여주지 말고 가능하면 잘못된 필드 가까이에 원인과 수정 방법을 표시하십시오. 비활성 상태로 이유를 숨기기보다 필요한 조건을 설명하십시오.

### 오버레이

| 필요                                  | 사용          | 선택 기준                                                     |
| ------------------------------------- | ------------- | ------------------------------------------------------------- |
| 짧고 비필수적인 설명                  | `Tooltip`     | 핵심 지침, 오류, 상호작용 콘텐츠를 넣지 마십시오.             |
| 현재 요소에 붙는 작은 상호작용·상세   | `Popover`     | 긴 작업이나 여러 필드는 `Dialog`를 사용하십시오.              |
| 현재 화면 위의 집중된 확인·입력·편집  | `Dialog`      | 배경 맥락과 병행해야 하는 상세는 `Drawer`가 적합합니다.       |
| 복구하기 어렵거나 영향이 큰 결정 확인 | `AlertDialog` | 일반 입력이나 쉽게 되돌릴 수 있는 작업에는 사용하지 마십시오. |
| 맥락을 유지하는 탐색·상세·보조 작업   | `Drawer`      | 짧은 확인만 필요하면 `Dialog`나 `Popover`를 사용하십시오.     |

오버레이에는 접근 가능한 제목, 명확한 닫기 경로, 예측 가능한 초기 포커스와 트리거로의 포커스 복귀를 제공하십시오. 긴 `Dialog`는 본문만 스크롤하고 제목과 주요 액션을 유지하십시오. `Drawer`의 `side`와 닫힘 방향을 일치시키십시오. 모바일 bottom sheet는 짧은 선택과 보조 작업에만 사용하십시오.

Drawer의 스크롤 본문은 `Drawer.Content`를 사용하십시오. 동일한 부품을 가리키던 `Drawer.Body`는 제공하지 않습니다.

손실이 작고 되돌릴 수 있는 작업은 `AlertDialog`를 반복해서 띄우기보다 실행 후 Undo를 제공하십시오. 삭제 확인에서는 대상, 결과, 복구 가능 여부를 설명하고 실행 버튼에 구체적인 파괴적 레이블을 사용하십시오.

### 피드백과 상태

| 필요                                     | 사용         | 지속 시간과 범위                                                          |
| ---------------------------------------- | ------------ | ------------------------------------------------------------------------- |
| 짧은 상태, 분류, 개수                    | `Badge`      | 객체나 행 가까이에 두고 문장이나 오류 설명을 대신하지 마십시오.           |
| 페이지 안에 유지되는 정보·성공·경고·오류 | `Alert`      | 관련 영역 가까이에 원인, 영향, 다음 행동을 표시하십시오.                  |
| 작업 후 일시적인 전역 결과               | `Toast`      | 사용자가 나중에 다시 봐야 하는 정보에는 사용하지 마십시오.                |
| 콘텐츠가 없는 이유와 다음 행동           | `EmptyState` | 제목, 짧은 설명, 가능한 대표 액션을 제공하십시오.                         |
| 구조를 예측할 수 있는 초기 로딩          | `Skeleton`   | 실제 콘텐츠의 수와 형태를 닮게 하고 상위 영역에 로딩 이름을 제공하십시오. |
| 측정 가능한 처리 진행 또는 대기          | `Progress`   | 값이 있으면 determinate, 알 수 없으면 indeterminate로 표현하십시오.       |

톤은 `neutral | info | success | warning | destructive` 의미를 일관되게 유지하십시오. 색상만으로 상태를 전달하지 말고 아이콘, 제목, 설명, 위치를 함께 사용하십시오. `warning`은 주의 후 진행할 수 있는 상태, `destructive`는 실패나 손실 위험에 사용하십시오.

클릭이나 입력에는 즉시 반응하고, 지연 작업에는 진행 중인 이유를 보여주십시오. 완료, 실패, 취소, 부분 성공을 구분하고 각각 다음 행동을 제공하십시오. Toast가 사라져도 중요한 오류와 복구 경로는 관련 영역에 남아야 합니다.

### 데이터와 레이아웃

표의 가로 스크롤과 영역 이름·안내는 `DataTableRegion`으로 구성하십시오. `Table`은 표 자체만 제공하며 `Table.ScrollArea`는 제공하지 않습니다. 표가 아닌 일반 영역에 사용자 정의 스크롤바가 필요하면 `ScrollArea`를 사용하십시오.

| 필요                                        | 사용              | 기준                                                                         |
| ------------------------------------------- | ----------------- | ---------------------------------------------------------------------------- |
| 행과 열을 비교하는 구조화 데이터            | `Table`           | 열 제목, 단위, 정렬 방향, 선택 이름, 빈·로딩 행을 제공하십시오.              |
| 가로 스크롤 가능한 테이블 영역              | `DataTableRegion` | 고유한 `label`과 작은 화면의 스크롤 힌트를 제공하십시오.                     |
| 필터 제어와 적용·초기화 액션                | `FilterBar`       | 필터와 결과의 관계가 보이게 하고 좁은 화면에서는 흐름 순서로 재배치하십시오. |
| 문맥·액션 Header와 Body를 연결하는 컨테이너 | `Panel`           | 구조만 공유하고 배경, padding, border와 overflow는 소비자가 정하십시오.      |

비교가 핵심이면 필요한 열을 한눈에 볼 수 있는 밀도를 유지하십시오. 모바일에서 표를 무조건 카드 목록으로 바꾸지 말고 비교 가치, 열 우선순위, 가로 스크롤 중 적합한 방식을 선택하십시오. 로딩 중 기존 데이터를 모두 지워 문맥을 잃게 하지 말고 갱신 상태를 구분하십시오.

`FilterBar`와 Table을 한 데이터 영역에 배치할 때는 필터 콘텐츠와 첫·마지막 열이 16px inline gutter를 공유하게 하십시오. Table의 `size`는 셀 내부 밀도만 바꾸며 영역의 바깥 정렬선은 바꾸지 않습니다. `table-layout: fixed`에서는 상태·숫자·날짜·액션 열에 콘텐츠 기반 최소 너비를 지정하고 주요 텍스트 열만 남은 폭을 사용하게 하십시오. `nowrap` 콘텐츠가 인접 열을 침범하면 안 되며, 전체 최소 너비가 화면을 넘으면 `DataTableRegion`에서 가로 스크롤하십시오.

## 표면, 색상, 타이포그래피

`plain | band | outline`은 장식이 아니라 그룹 경계를 표현하는 표면입니다.

- `plain`: 주변 레이아웃의 간격과 정렬만으로 관계가 충분할 때 사용하십시오.
- `band`: 툴바나 필터처럼 페이지 폭의 기능 영역을 배경으로 구분할 때 사용하십시오.
- `outline`: 독립적인 경계와 상호작용 영역이 필요할 때 사용하십시오.

부모와 자식에 같은 테두리, radius, 그림자를 반복하지 마십시오. 내부 그룹은 먼저 간격, 정렬, 제목, divider로 구분하십시오. 카드나 패널은 독립된 정보, 액션, 상태를 소유할 때만 추가하십시오.

### 색상 체계

색상은 `원시 팔레트 → 의미 토큰 → 컴포넌트 tone·appearance → 상태` 순서로 적용하십시오.

- `--city-palette-*`는 제품별 의미 토큰을 정의하는 재료입니다. 재사용 컴포넌트에 직접 적용하지 마십시오.
- `--city-color-*`는 background, surface, interaction, action, feedback, effect 역할을 정의합니다. city-ds 컴포넌트와 소비 화면은 먼저 의미 토큰을 사용하십시오.
- `tone`은 `neutral | info | success | warning | destructive` 의미이고, 이를 지원하는 컴포넌트의 `appearance`는 `solid | subtle | outline` 표현 강도입니다. 같은 tone은 컴포넌트가 달라도 같은 의미를 유지해야 합니다.
- `solid`는 주요·위험 액션과 짧은 Badge에 사용하십시오. 넓은 Alert는 subtle 또는 outline을 사용하고, Toast는 appearance 없이 background 92%와 tone 원색 8%를 혼합한 배경, tone 원색 border·텍스트를 사용하십시오.
- white·neutral 계열을 제외한 유색 solid는 모든 테마에서 `neutral-50` 전경과 일반 텍스트 4.5:1 이상 대비를 이루는 어두운 fill만 사용하십시오. 밝은 유색 면이 필요하면 전경을 어둡게 바꾸지 말고 subtle 또는 outline을 사용하십시오.
- primary·destructive의 hover·active, feedback의 foreground·surface·border는 공개 토큰을 사용하십시오. `/10`, `/40`, `/90`처럼 임의 투명도로 상태색을 만들지 마십시오.
- Tooltip은 inverse, Dialog·Drawer·Popover 배경은 backdrop, Skeleton highlight는 shimmer 역할을 사용하십시오.

한 액션 그룹에는 원칙적으로 하나의 primary만 두십시오. `warning`은 확인 후 진행할 수 있는 상태, `destructive`는 실패나 손실 위험에 사용하십시오. 브랜드 색을 추가하더라도 action, status, destructive 의미와 충돌시키지 마십시오.

상태를 색상 하나에 맡기지 말고 아이콘, 제목, 레이블, 위치 또는 ARIA 상태를 함께 제공하십시오. 일반 텍스트는 4.5:1, 큰 텍스트·아이콘·focus 표시는 3:1 이상의 대비를 유지하고 라이트, 다크, 시스템 테마에서 default, hover, active, selected, invalid, focus, disabled를 확인하십시오. disabled는 컴포넌트 전체 opacity를 낮추는 예외입니다.

색상 토큰 목록과 Light·Dark 비교는 Storybook의 `기초/디자인 토큰/색상`, 컴포넌트 선택 규칙은 `디자인 패턴/Color`를 참고하십시오.

### 모션 체계

모션은 장식보다 상태 변화와 공간 관계를 설명해야 합니다. duration은 `fast 80ms | normal 120ms | slow 160ms | xslow 240ms` 네 단계를 사용하고, 기본 transition은 `normal`과 `ease-in-out`을 조합하십시오. 즉각적인 indicator 반응은 fast, 일반적인 Control 상태 변화는 normal, 콘텐츠 크기 변화는 slow, 큰 레이어 변화는 xslow를 사용하십시오. Density나 Control Size만으로 duration을 바꾸지 마십시오.

왕복하거나 중간에 취소할 수 있는 상태 변화에는 진행값이 역방향으로 움직이지 않는 easing을 사용하십시오. bounce·spring은 공통 토큰으로 제공하지 않으며, 되돌아가지 않는 일회성 완료 피드백을 프로젝트 패턴으로 별도 정의할 때만 검토하십시오. 열기·닫기, 선택·해제, 이동 방향이 바뀌는 전환에는 사용하지 마십시오.

콘텐츠 고유 높이를 펼치고 접을 때 임의의 `max-height`를 추정하지 마십시오. Grid container의 `grid-template-rows`를 `0fr`과 `1fr` 사이에서 전환하고, 직접 자식에 `min-height: 0`과 필요한 overflow 처리를 적용하십시오. 사용자가 reduced motion을 요청하면 이동, 크기 변화와 반복 애니메이션을 제거하되 최종 상태는 즉시 구분되어야 합니다.

색상 외 간격, 글꼴, radius, 그림자와 모션도 `--city-*` 토큰을 사용하십시오. 세부 역할과 예시는 Storybook의 `디자인 패턴/Motion/Overview`를 참고하십시오.

제목 수준은 문서 구조를 따르십시오. 글자 크기로 heading 순서를 흉내 내지 마십시오. 보조 텍스트는 낮은 대비를 사용할 수 있지만 읽을 수 있어야 하며, 오류나 필수 지침을 보조 장식처럼 약하게 만들지 마십시오.

## 반응형과 콘텐츠

- DOM과 키보드의 읽기 순서를 먼저 올바르게 만들고 CSS로 재배치하십시오.
- 작은 화면에서는 보조 액션을 다음 줄이나 Menu로 이동하되 주요 액션은 찾을 수 있게 유지하십시오.
- 긴 레이블과 현지화 문구는 줄바꿈, 영역 확장, 공통 반응형 규칙으로 처리하십시오. 한 요소만 글자를 줄여 맞추지 마십시오.
- 오버레이와 팝업이 viewport 밖으로 나가지 않게 하고 긴 본문은 적절한 내부 영역에서 스크롤하십시오.
- hover 없이도 모든 행동을 발견하고 실행할 수 있게 하십시오.
- 로딩, 오류, 선택, 포커스, disabled 상태는 라이트·다크 테마와 키보드에서 확인하십시오.

## 접근성과 상태 점검

Base UI가 제공하는 키보드, 포커스, ARIA, 상태 동작을 재구현하지 마십시오. 합성 API는 `render`를 사용하십시오. Toast의 queue·수명·swipe·live region은 Sonner를 사용하고, `Toaster`와 `toast()` 위에 city-ds의 tone·아이콘·모션 규칙만 적용하십시오.

- 모든 폼 제어, 아이콘 버튼, ToggleGroup, Toolbar, table region에 접근 가능한 이름이 있습니까?
- heading 순서와 landmark가 시각 배치와 같은 문서 구조를 표현합니까?
- Tab, Shift+Tab, 방향키, Enter, Space, Escape로 흐름을 완료하고 닫은 뒤 돌아올 수 있습니까?
- focus ring이 모든 표면과 테마에서 보입니까?
- 오류는 원인, 영향, 복구 방법을 설명하고 해당 필드나 영역과 연결됩니까?
- loading, empty, error, success, disabled, permission 상태에서 다음 행동이 분명합니까?
- 터치 대상, 대비, 읽기 순서, 애니메이션이 접근성을 약화시키지 않습니까?

## 조합 예시

### 데이터 관리 화면

`Breadcrumbs` > 페이지 제목과 대표 `Button` > `FilterBar` > `DataTableRegion` 안의 `Table` > `Pagination` 순서로 구성하십시오. 행 상세는 `Drawer`, 편집은 `Dialog`, 복구하기 어려운 삭제는 `AlertDialog`, 짧은 저장 결과는 `Toast`를 사용하십시오.

### 설정 폼

관련 설정을 `Fieldset`으로 묶고 각 입력은 `Field`로 설명과 오류를 연결하십시오. 즉시 적용되는 이진 설정은 `Switch`, 제출 시 확정되는 복수 선택은 `CheckboxGroup`, 짧은 단일 선택은 `RadioGroup`을 사용하십시오. 폼 끝에는 같은 크기의 보조 버튼과 하나의 `primary` 저장 버튼을 두십시오.

## 최종 품질 기준

동일한 역할·위계·상태에는 동일한 컴포넌트, 크기, 밀도, 톤, 표면을 적용하십시오. 예외가 필요하면 콘텐츠 길이, 상호작용, 위험, 반응형 같은 반복 가능한 의미 차이로 설명할 수 있어야 합니다. 정상 경로만 완성하지 말고 지연, 빈 상태, 실패, 권한 상실, 긴 콘텐츠, 키보드, 작은 화면에서도 사용자가 목표를 완료하거나 안전하게 복구할 수 있게 하십시오.
